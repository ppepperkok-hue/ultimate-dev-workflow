# 实施文档拆解（Implementation Docs）

## 本步定位

把当前大阶段拆成一份「实施真元文档」——这个阶段的**单一可信来源（SSOT）**：AI 照着它写，你照着它验收。

为什么还要再拆一层：大阶段通常很粗。直接丢给 AI 一句话，它会自己脑补先做什么、后做什么、做到什么程度，脑补出来的往往不是你要的；AI 还会偷懒，快速写一堆看似在干活、实际没意义的东西。所以在写代码之前，每个大阶段都要配一份足够细的实施文档。

## 三大核心（拆解的细度标准）

1. **明确执行目标**：AI 知道这一段要做什么、做到什么程度算完成。
2. **划定任务边界**：AI 知道哪些东西现在先不要碰（暂时不做什么）。
3. **制定验收标准**：验收标准和验证方式一起写进去，每一步能执行、能验收、有边界。

不是越细越好，而是细到 AI 能回答这三件事就够了。

## 拆解结构

大阶段 → 子阶段 → 步骤（第一步、第二步、第三步……）。

## 粒度对照（别混）

- **01d 可执行单元**：立项阶段的 backlog 单位（功能级任务）。
- **子阶段 / 步骤**：实施真元文档内的执行单位；步骤是最小交付单位。
- **任务包**（[09-role-division.md](09-role-division.md)）：总监把一个或多个步骤打包派给 CLI 的派发单位。

关系：01d 单元 → 拆成步骤 → 步骤打包成任务包。

## 执行方式

1. **只拆当前马上要做的这个大阶段**。后面的大阶段先保留大方向，不扣详细步骤——需求会变，提前拆细大半白做；做完一个大阶段，再拆下一个，一个一个来。
2. **让 AI 拆文档**（示例指令是用户对工程总监说的；总监拆好后按 09 打包派给 CLI 执行）：

   > 请根据功能清单和阶段计划，把当前这个大阶段细化成一份详细的实施真元文档。先把这个阶段拆成几个子阶段，每个子阶段再拆成更小的步骤。逐条说明每一步要做什么、做到什么程度、涉及哪些功能、验收标准是什么、用什么方式验证、暂时不做什么。先不要写代码。

3. **拆完一定要看**：这是写代码前最后一次和 AI 对需求的机会。
   - 对照原始需求检查有没有偏差；有偏差先找出来讨论，讨论完让它改。
   - 看不懂就让它用大白话一条条解释，不要怕麻烦。
   - 把自己的原始需求重新贴给 AI，让它对照实施真元文档检查冲突；有问题先列出来，先别写代码。
4. 评审通过后固定文档路径；每次开工前明确要求 AI 对照这份文档执行。

## 与 Agent 宪法的分工

- **Agent 宪法**管 AI 怎么做事（行为规则）。
- **实施真元文档**管这个大阶段具体做什么（内容与验收）。
- 聊天里临时冒出来的想法不是不能改，但要先回写进实施真元文档，才算正式变更。

## 地基底线（拆解与实施中都不能破）

- 动手写代码后，业务细节可以调，**底层架构不能随手翻**。
- 技术栈、目录结构、数据库表设计、核心字段存储、登录权限、支付流程——这些是地基。改动会碰到它们时：先不实现，先给影响评估和调整方案。
- 判断不了就直接问 AI：「这个改动会不会影响技术栈、目录结构、数据库表、核心字段、登录权限、支付流程？」会，就先停下讨论，让 AI 评估影响范围再给稳妥方案。
- 绝不图省事丢一句「先满足需求再说」就让它改——AI 很可能为了照办转头破坏架构，前面立项、选型、项目架构全白做。

## 产出

- 实施真元文档（`docs/implementation/`），只覆盖当前大阶段
- 评审记录：需求对照结果、问题清单

## 验收门

- 只拆了当前大阶段，未预拆后续阶段
- 每一步都有：做什么、做到什么程度、验收标准、验证方式、暂时不做什么
- 与原始需求对照无冲突，或冲突已讨论解决
- 用户确认

通过后进入「分阶段推进验收」。
