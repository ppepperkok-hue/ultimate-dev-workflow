# 项目架构（Architecture）

## 本步定位

把技术栈落成「最小可运行架构 + 一套通用规则」，而不是一次性搭全所有功能的架构。

## 核心：最小架构与统一规则

- **避免全量开发功能**：立项清单的功能不等于本期架构，只建支撑首个里程碑的最小范围。
- **构建最小架构**：先让最小链路真实跑通，再谈扩展。
- **把通用规则定下**：目录、命名、错误、配置、接口、测试、提交的规则一次性定死，写成可检查的文档。
- **以后每个功能遵循统一开发规则**：新功能按模板增量接入，禁止另起炉灶。

## 四步流程（顺序执行）

1. **确定最小架构范围** — [03a-minimum-scope.md](03a-minimum-scope.md)
2. **定义通用规则** — [03b-common-rules.md](03b-common-rules.md)
3. **搭建最小骨架** — [03c-minimal-skeleton.md](03c-minimal-skeleton.md)
4. **建立功能接入规则** — [03d-feature-extension.md](03d-feature-extension.md)

每一步先读对应文档，产出写入 `docs/architecture/` 下对应文件；四步完成后汇总并交用户确认。

## 原则

- 边界先于代码：模块边界和接口可讲清再写码。
- 配置驱动：环境差异进配置，不硬编码。
- 失败显式化：错误有明确路径，不静默吞掉。
- 幂等：重复执行结果一致。
- 最小复杂度：能简单就不引入框架、服务、抽象。
- 核心优先：与「最小架构 + 统一规则」冲突的设计一律削减。

## 验收门

- 架构范围只支撑首个里程碑，无全量功能
- 通用规则全部有检查手段（lint/测试/模板）
- 最小骨架真实跑通，验证命令可复现
- 功能接入模板实测可用，新功能有统一路径
- 用户确认

通过后进入 Agent 宪法。架构变更先改文档再改代码。
