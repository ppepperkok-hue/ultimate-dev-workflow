# 项目架构（Architecture）

## 目的

把技术栈落成可实现的模块边界：先画边界和数据流，再写代码。

## 输入

- 已确认的立项清单 + 技术栈决策

## 交付物（骨架）

1. **模块划分与边界**：每个模块的职责、依赖方向（禁止反向/循环依赖）。
2. **数据流与状态**：核心路径的时序，含错误与异常路径。
3. **目录骨架**：可直接落盘的项目目录结构。
4. **接口契约**：外部接口与内部模块接口，含入参/出参/错误约定。
5. **配置策略**：哪些东西进配置、环境如何区分、敏感信息如何注入。
6. **可观测性**：日志、指标、追踪的最小方案。
7. **部署拓扑**：运行环境、进程/服务边界、数据存储位置。
8. **架构图**：mermaid 图，随文档维护。

产出归档为 `docs/architecture.md`，目录骨架可直接用于 Phase 1 初始化。

## 原则

- 边界先于代码：写码前模块边界和接口必须可讲清。
- 配置驱动：环境差异进配置，不硬编码。
- 失败显式化：错误有明确路径，不静默吞掉。
- 幂等：重复执行同一操作结果一致。
- 最小复杂度：能简单就不引入框架、服务、抽象。

## 验收门

- 模块边界可画出、依赖无环
- 关键接口有签名和错误约定
- 目录骨架可落盘，架构图与文档一致
- 关键架构风险有对策

通过后进入 Agent 宪法。架构变更需先改文档再改代码。
