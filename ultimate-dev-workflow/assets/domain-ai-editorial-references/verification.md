# 验证纪律与审查流程

## 每次改动必跑的验证

```bash
# 后端全量测试（必须隔离：临时库、不触发真实 webhook）
python run_tests.py

# 工作流语义校验（节点可达、字段引用、表达式语法、尾链、错误分支）
node tools/validate_workflow_deep.mjs

# 前端
cd webapp && npm test && npm run build
```

新增代码必须配测试；修 bug 先复现或写失败测试。

## 工作流语义校验清单

- 所有节点引用可达（BFS）；无出边的非终端节点报错。
- main/error 分支终点必须可达「释放锁/结束」。
- 数据流：下游表达式引用的上游输出字段必须存在（如排版必须从润色取正文，不能从摘要取）。
- executeCommand 参数化：command 是解释器，commandArguments 首元素不得再是解释器；路径走 env。
- 表达式语法：jsonBody 里的 JS 模板字符串逐节点语法检查，消除假绿灯。
- 尾链：收尾固定顺序（如 读当前书 → 查存稿 → 生成/发布 → 汇总 → 记录 → 阅读数据 → 日记 → 知识库同步 → 行动项回填 → 释放锁）。
- 错误分支：关键 LLM/发布节点 continueErrorOutput + 显式留痕；合并节点端口唯一连续且与 numberInputs 一致。
- 幂等：run_id 用执行 ID，同一执行内重复输入不重复记账。

## 测试隔离规则

- 测试一律用 `tempfile.mkdtemp()` 临时库，绝不写 `demo.db`。
- webhook/外部 API 调用全部 mock；`run_tests.py` 防止测试触发真实 n8n。
- 数据插入用最小必填字段（注意 NOT NULL 列，如 novels.title/genre/premise、chapters.outline）。

## 审查流程（每个「再审查一遍」都要产出报告）

1. 原则：证据优先（文件:行号/API 响应/测试输出）；字段对照；动作对照；P0–P3 分级。
2. 范围：前端逐组件 / 后端逐 handler / 工作流拓扑 / 端到端数据链路。
3. 报告落 `docs/reviews/YYYYMMDD-<scope>-review.md`，含：范围与方法、总评、问题清单（带证据与建议）、确认无问题的模块、验证记录、后续建议。
4. 修复后把验证结果写进同一报告的「修复记录」。

## 严重程度分级

| 级别 | 含义 | 例子 |
| --- | --- | --- |
| P0 | 数据损坏/丢钱/无法运行 | 发布空章、覆盖真实数据、数据库损坏 |
| P1 | 影响真实使用 | 列表截断、日期统计错、动作无效 |
| P2 | 展示错误/不一致/死模块 | 节点数写死、上限不一致、无数据源区块 |
| P3 | 小问题/体验 | 缺筛选、文案、快捷键、性能 |

## 端到端走查顺序（新书 → 发布）

新书会议 → 确认创意 → 建书/绑定 → 日更（生成→审稿→质量门→发布）→ 落库 → 阅读数据回流 → 全员日记 → 设定知识库同步 → 行动项回填 → 释放锁。

走查时观察：执行记录状态、失败是否显式落库、番茄侧复核、锁是否释放、成本是否入账。
