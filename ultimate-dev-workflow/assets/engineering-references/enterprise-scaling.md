# 企业级扩展：环境、发布安全与事故响应

当项目进入「多人协作、高可用要求、发布不能出错」的阶段时，按本文件扩展。小项目/学习项目不要照搬——复杂度是买来的，只为明确的风险买单。

## 1. 环境分层（dev → test/QA → staging → prod）

| 环境 | 数据 | 目的 |
| --- | --- | --- |
| 开发（dev） | 模拟数据 | 每天集成、自动部署，开发者协作验证「本地能跑 ≠ 环境能跑」 |
| 测试/QA | 接近真实的数据集 | 产品经理/测试工程师手工验证，跑负载与快照测试 |
| 预发布（staging） | 近生产数据 | 客户/测试用户验收，发布前最后一道闸 |
| 生产（prod） | 真实数据 | 用户使用；配置变更必须走流水线，不许手点控制台 |

原则：

- 每次合并到 dev 分支自动部署 dev 环境，集成频率越高冲突越少。
- 环境间的差异要显式记录（数据规模、配置、开关），不要「环境行为不一致但没人知道为什么」。
- 预发布环境跑负载测试和快照测试，验证容量与视觉/行为回归。

## 2. 基础设施即代码（IaC）

- 用代码描述全部基础设施（计算、队列、数据库、CDN、配置），一条命令拉起整套环境。
- 收益：环境可复制（dev/staging/prod 同构）、几百个资源不用手点控制台、配置变更可评审可回滚、随时开实验环境。
- 反模式：有人手动改了云控制台但没同步代码 → 环境漂移，下次部署直接覆盖或崩。
- 最小可行：即使只有一台服务器，也把启动脚本/部署脚本入库（我们的 `start_n8n.ps1` + env 参数化就是这个思路的缩影）。

## 3. 发布安全

### 3.1 特征标志（feature flag）

- 未完成的功能默认关闭，代码先上线，开关在数据库/配置里控制。
- 好处：发布与上线解耦，代码随时可合，功能按需灰度；出问题关开关即止血。
- 纪律：标志要有负责人与清理计划，长期不清理会变成技术债。

### 3.2 回滚

- 每次发布要能回滚：优先回滚单个变更（如单个函数版本），而不是整体回退。
- 回滚 ≠ 修 bug：回滚是止血，修 bug 是根治，两者都要做。

### 3.3 热修复（hotfix）

- 生产出问题时：从主干拉独立分支 → 快速修复 → 高层审批 → 部署 → 把修复合并回 dev/主干，防止分叉。
- 修复后必须同步到所有下游分支，否则下次合并会把旧代码带回来。

## 4. 高可用与多区域

- 「五个九」（99.999%）约等于一年停机 30 分钟到 1 小时；要求越高，架构成本越高。
- 多区域模式：
  - 主动-被动：主区故障自动切到备区，实现简单；
  - 双活：按地域就近接入，数据库双向复制，延迟低但复杂度高。
- 数据有法律边界（跨境流动限制），多区域复制要过合规，不是纯技术开关。
- 对学习项目：先保证「备份 + 可重建」，再谈多区域。

## 5. 事故响应三道防线

1. 用户/监控反馈发现异常；
2. 关特征标志立即止血；
3. 回滚部署；不能回滚则走热修复。

纪律：先止血、再定位、后根治；事故要复盘并写进文档（时间线、根因、预防项）。

## 6. 复杂度纪律

- 复杂度只在两种情况下引入：风险高（医疗/金融/百万用户核心链路）或明确收益（提升效率/质量）。
- 小团队/学习项目默认走简单路径：主干开发 + 自动构建部署 + 快速修复（「30 分钟推出修复」）。
- 每加一层环境、一个流程，都要能回答「它防止了什么灾难」；答不上来就不加。
