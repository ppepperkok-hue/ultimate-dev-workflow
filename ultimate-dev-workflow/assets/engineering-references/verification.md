# 验证纪律与审查流程

## 每次改动必跑的验证

根据项目类型选择，至少包含测试与构建：

```bash
# 后端
python run_tests.py            # 或 pytest / 对应测试命令

# 前端（如有）
cd webapp && npm test && npm run build

# 生成物校验（如有生成器/工作流）
node tools/validate_workflow_deep.mjs   # 或等价校验脚本
```

新增代码必须配测试；修 bug 先复现或写失败测试；视觉工作检查渲染结果（截图/打开页面）。

## 生成物/配置校验清单

- 所有节点/模块引用可达；无出边的非终端节点报错。
- 分支终点必须可达「结束/释放/清理」。
- 数据流：下游引用上游输出字段必须存在。
- 参数化：解释器/根路径走 env；参数首元素不得是解释器。
- 表达式语法：生成物里的模板表达式逐项语法检查，消除假绿灯。
- 幂等：同一执行 ID 重复输入不重复记账/不重复副作用。

## 测试隔离规则

- 测试一律用临时目录/临时库，绝不写生产数据库。
- 外部调用（webhook/API/平台）全部 mock；测试入口防止触发真实外部系统。
- 数据插入用最小必填字段（注意 NOT NULL 列）。
- 测试要能脱离网络与密钥运行。

## 审查流程（每个「再审查一遍」都要产出报告）

完整的分域漏洞清单、静态扫描命令、动态验证与报告模板见 `audit.md`；本节是核心规则。

1. 原则：证据优先（文件:行号/API 响应/测试输出）；字段对照；动作对照；P0–P3 分级。
2. 范围：前端逐组件 / 后端逐 handler / 数据链路端到端。
3. 报告落 `docs/reviews/YYYYMMDD-<scope>-review.md`，含：范围与方法、总评、问题清单（证据+影响+建议）、确认无问题的模块、验证记录、后续建议。
4. 修复后把验证结果写进同一报告的「修复记录」。

## 严重程度分级

| 级别 | 含义 | 例子 |
| --- | --- | --- |
| P0 | 数据损坏/丢钱/无法运行 | 发布空内容、覆盖真实数据、数据库损坏 |
| P1 | 影响真实使用 | 列表截断、统计错、动作无效 |
| P2 | 展示错误/不一致/死模块 | 数字写死、上限不一致、无数据源区块 |
| P3 | 小问题/体验 | 缺筛选、文案、快捷键、性能 |

## 端到端走查顺序（通用模板）

入口（定时/手动/事件）→ 预检（密钥/预算/幂等/锁）→ 核心处理 → 外部调用（如发布/通知）→ 落库 → 数据回流/汇总 → 收尾（清理/释放锁/记录日志）。

走查时观察：

- 执行状态与耗时；
- 失败是否显式留痕（错误码/日志/状态字段）；
- 外部侧结果复核（平台/API 侧对账）；
- 锁是否释放；
- 成本/用量是否入账；
- 重复触发是否幂等。
