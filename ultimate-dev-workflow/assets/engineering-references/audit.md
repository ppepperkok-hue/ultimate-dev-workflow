# 通用审查流程（Agent 自审手册）

目标：让 agent 在没有人工提示的情况下，按本流程系统地找漏洞。任何「再审查一遍」「检查有没有问题」「看看哪里会挂」的请求，都按本流程执行并产出报告。

## 1. 触发时机

- 提交/合并前必须自审；
- 新功能或大改动完成后；
- 用户明确要求「审查 / 找漏洞 / review / 检查」；
- 端到端跑通后复检（审查不是测试的替代，是测试之上的第二层）。

## 2. 审查准备

1. 跑测试与构建：`python run_tests.py` / `npm test` / `npm run build` / 对应校验脚本，先确认基线。
2. 读架构：目录结构、配置加载、数据流入口 → 核心处理 → 外部调用 → 落库 → 收尾。
3. 列出审查范围：本次改动涉及的文件、模块、数据链路；未涉及的范围也抽查关键路径。
4. 打开「证据纪律」：每条结论必须有文件:行号、API 响应、命令输出或复现步骤；不允许「感觉有问题」。
5. **族标签（类级治理前置）**：每条发现必须带反模式族标签 `F1`–`F12`（定义见 SKILL.md「反模式族级治理」）。报告条目格式统一为：`[级别|族] 描述 — 文件:行号`，例如 `[P2|F1] json.loads 无异常保护，脏配置拖垮接口 — web_api.py:660`。带族标签后，主 agent 归族、族级扫描、族级任务包可以直接自动化；无法归族的发现标 `F0`（独特问题）。多族命中时写主族标签并在描述里注明次族。

## 3. 静态扫描（先跑自动化，再人工）

用 rg / 编辑器全局搜以下模式，命中即进入人工确认：

```bash
# 裸异常（吞错）
rg -n "except\s*:|except Exception" --glob '*.py' --glob '*.js' --glob '*.mjs'

# 硬编码路径 / 机器相关（单引号保证 PowerShell 与 bash 一致）
rg -n 'C:\\|/home/|/Users/|D:\\|YOUR_|TODO|FIXME|HACK|XXX'

# 空响应当成功 / 静默返回
rg -n "return \"\"|return None|or \"\"|or \[\]" --glob '*.py'

# 无锁写入 / 直接写库
rg -n "INSERT INTO|UPDATE .*SET" --glob '*.py' | head -200

# 子进程 / 命令拼接（注入面）
rg -n "subprocess|os\.system|shell=True|executeCommand|eval\(|exec\("

# 硬编码密钥 / Token / Cookie
rg -n "api[_-]?key|token|cookie|password|secret" -i --glob '!*.md' --glob '!*.example'

# 前端写死数字 / UTC 日期
rg -n "toISOString|60 节点|节点数|limit.*5|Math\.random"

# 测试接触真实环境
rg -n "demo\.db|localhost:5678|webhook|real" tests/ --glob '*.py'

# 动态 SQL 拼接（占位符错位 / 注入面）
rg -n 'IN \(" \+|%s"|execute\(f"|VALUES\(" \+' --glob '*.py'

# 批量改名/重构遗漏（旧包名、旧目录、旧品牌引用）
rg -n 'novel_pipeline|webnovel-pipeline|pipeline' --glob '*.py' --glob '*.js' --glob '*.json' --glob '*.md'

# PowerShell 脚本中文与编码（PS 5.1 按 ANSI 读 UTF-8 无 BOM 会解析失败）
rg -n 'Write-Host "[^"]*[\u4e00-\u9fff]' --glob '*.ps1'
```

命中项逐条判断：是反模式还是合理设计（如显式容错）；合理则记录「已确认无害」，不合理则升级为漏洞条目。

### 实战坑速查（2026-08 新增）

- **broadcast 按接收者逐条落库**：`mailroom.broadcast` 给 N 个 agent 会落 N 条消息，断言数量要按 `len(AGENT_NAMES)` 而不是 1；
- **动态 IN 子句占位符错位**：两个不同长度的 `IN (...)` 共用同一个占位符串会报「Incorrect number of bindings」；每个 IN 单独生成占位符；
- **批量改名要扫描被跳过的目录**：批量替换脚本的 SKIP_DIRS 可能漏掉 desktop/node_modules 等，改名后必须全局 `rg` 旧包名做零残留断言；
- **PowerShell 5.1 读 UTF-8 无 BOM 的 .ps1**：中文字符串可能被按 GBK 误读导致「字符串缺少终止符」；脚本文件要么带 BOM，要么输出全 ASCII；
- **dry-run 不落库 vs 测试断言落库**：dry-run 模式设计为不写 `daily_runs`，测试断言落库要用非 dry-run 路径或手动造行，别把「dry-run 没落库」当 bug。

## 4. 分域漏洞清单

### 4.1 逻辑与边界

找什么：

- 空输入、None、空字符串、空列表是否被当作成功？
- 数值边界：0、负数、上限、溢出、除零？
- 状态机：每个状态都有合法迁移吗？非法状态怎么处理？
- 幂等：同一输入重复执行（重复触发/重复提交）是否产生重复副作用？
- 超时：外部调用有没有超时？后台任务有没有总时长上限？
- 时区：今日/本周统计是否 UTC 与本地混用？
- 分支覆盖：if/else 的所有分支都有输出吗？缺分支会怎样？

### 4.2 数据层

找什么：

- 空载荷是否建垃圾行？
- 删除主行是否清理全部子表（孤儿引用）？
- 唯一约束是否覆盖业务唯一性（如章节序号、任务 ID）？
- 迁移是否兼容旧库？迁移失败会怎样？
- 写入是否幂等（upsert / 幂等键）？
- 查询是否用参数绑定（防注入）？

### 4.3 并发与后台任务

找什么：

- 定时 + 手动是否可能双发？有没有共享锁？
- 锁：原子创建？陈旧回收阈值是否大于单次运行时长？所有退出路径（成功/失败/异常）都释放吗？有手动释放工具吗？
- 后台线程：重启后是否变僵尸占位？心跳/自愈？取消是否在写入前校验状态？
- 全局锁是否持太久（锁粒度）？

### 4.4 外部集成

找什么：

- 接口路径、请求体、鉴权、签名是否与真实请求一致（还是猜的）？
- 错误码是否映射到本地状态与用户可读信息？
- 瞬时错误是否重试？重试是否有上限与退避？其他错误是否直接失败？
- 限额/风控：每日上限、字数上限、频率限制有没有预检与熔断？
- 失败后是否保留可补发状态？
- 凭据（Cookie/Token）过期是否有检测与提示？

### 4.5 安全

找什么：

- 密钥/Tok/Cookie 是否硬编码在代码、日志、文档、前端？
- 用户输入是否直接拼进 SQL、命令、HTML、URL？
- 文件读写是否有路径穿越防护（绝对路径白名单、`..` 过滤）？
- 本地服务：是否只监听本机？CORS/Origin 校验？POST 是否校验 Content-Type 与 body 大小？可选鉴权是否生效？
- 错误信息是否向客户端泄露内部细节（堆栈、路径、SQL）？
- 日志/审计是否记录敏感数据？

### 4.6 生成物与配置

找什么：

- 生成物（工作流 JSON、模板、代码生成）是否由生成器产出且未被手改？
- 模板表达式是否有语法校验（假绿灯）？
- 模板字符串转义是否正确（`{}`、引号、`$()`）？
- 路径/解释器是否 env 参数化？参数首元素是否重复解释器？
- 换环境只需要改配置吗？`.env.example` 是否覆盖全部运行参数？

### 4.7 前端

找什么：

- 每个显示字段在后端 API 有出处吗（无数据源 = 死模块）？
- 每个按钮有真实动作链吗（UI → API → handler → 副作用 → 刷新）？
- 状态三态：加载/空/错误都有 UI 吗？页面级错误边界？
- 实时通道：推送快照是否覆盖/截断轮询数据？断连有兜底吗？
- 本地日期 vs UTC；硬编码数字（节点数/上限）与后端一致吗？
- 危险操作（删除/发布/暂停）有确认吗？操作后状态刷新吗？
- 渲染用户内容时转义了吗（XSS）？

### 4.8 可观测性

找什么：

- 有没有「看起来成功但什么都没发生」的路径（空响应、静默 except、continue 吞错）？
- 关键动作（发布、写库、会议、外部调用）有日志/留痕/审计吗？
- 失败时有错误码与原因吗？用户/面板能看到吗？
- 告警：预算超限、连续失败、断更风险有通知吗？

### 4.9 性能与资源

找什么：

- 无限重试/无限轮询/无限循环？
- 轮询频率是否过高（打爆本地 API）？
- 大对象是否常驻上下文/内存（应文件传递或截断）？
- 定时任务是否叠加（上次没跑完下次又开始）？
- 数据库查询是否有全表扫描风险（大表无索引）？

### 4.10 测试与交付

找什么：

- 新代码有测试吗？修 bug 有失败测试先复现吗？
- 测试隔离：临时库、mock 外部调用、不触真实 webhook？
- 端到端是否实跑过？单元全绿 ≠ 链路能跑。
- 文档（README/状态/版本号/节点数/测试数）与代码一致吗？「已实现」是否真有实现？
- 待办/已知限制是否如实列出？

## 5. 漏洞分级

| 级别 | 含义 | 例子 |
| --- | --- | --- |
| P0 | 数据损坏/丢钱/无法运行/安全泄露 | 发布空内容、覆盖真实数据、密钥进仓库、命令注入 |
| P1 | 影响真实使用 | 列表截断、统计错、动作无效、失败静默 |
| P2 | 展示错误/不一致/死模块 | 数字写死、上限不一致、无数据源区块 |
| P3 | 小问题/体验 | 缺筛选、文案、快捷键、性能 |

## 6. 动态验证（静态找不到的）

对高危结论必须动态验证：

- 构造边界输入跑一次（空输入、超限、重复触发、并发触发）。
- 外部集成：真实小规模调用一次；构造失败场景（错误码/超时）验证处理。
- 并发：同时手动 + 定时触发，确认只有一个执行。
- 重启恢复：杀掉服务/进程重启，确认无僵尸、锁可释放、任务不双发。
- 端到端：入口 → 核心 → 外部 → 落库 → 收尾，逐节点观察。

## 7. 审查报告模板

```markdown
# <范围>审查报告（YYYY-MM-DD）

## 审查范围与方法
（文件/模块/数据链路清单 + 执行的命令与基线结果）

## 总评
（3-5 句：骨架是否健康、最值得修什么）

## 问题清单
（P0/P1/P2/P3 分级；每条含证据 文件:行号 / 输出、影响、修复建议）

## 确认无问题的模块
（逐个说明为什么安全，防止重复审查）

## 验证记录
（命令与输出摘要：测试数、构建、静态扫描命中、动态验证）

## 后续建议
（修复优先级、需要补的测试、需删除的死代码）
```

## 8. 修复后闭环

1. 每条漏洞先写失败测试或复现步骤；
2. 修复；
3. 跑全量验证（测试 + 构建 + 校验脚本）；
4. 在报告「修复记录」里登记：证据、验证结果、是否引入新问题；
5. 更新文档数字与状态。
